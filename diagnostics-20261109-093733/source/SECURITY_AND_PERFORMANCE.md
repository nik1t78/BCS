# BCS — безопасность и производительность

## Что изменено в этой сборке

- Убраны небезопасные пароли БД и Redis по умолчанию из Docker Compose. При отсутствии `DB_PASSWORD`, `DB_ROOT_PASSWORD` или `REDIS_PASSWORD` Compose остановится с понятной ошибкой вместо запуска с известными паролями.
- В `.env.example` оставлены явные заполнители для трёх разных секретов. Перед запуском замените каждый на собственное случайное значение.
- Для PHP-FPM заданы умеренные лимиты процессов и `pm.max_requests`, чтобы не создавать 12 PHP-процессов в контейнере с ограниченной памятью.
- Включена оптимизация OPcache для production-контейнера. После обновления кода контейнер нужно пересобирать/перезапускать, что уже предусмотрено процедурой развёртывания.
- Добавлен индекс `meetings(room, date, status)` для ускорения проверки занятости конкретного зала. Это обычный индекс, не UNIQUE: он не запрещает параллельные ВКС в разных залах.
- Серверная проверка занятости остаётся привязанной к имени конкретного физического зала. Онлайн-встречи без зала не блокируют друг друга. Встречи в разных залах могут начинаться одновременно.

## Правило одновременных ВКС

Разрешено:

- Зал «Большой» — 10:00–11:00 и зал «Малый» — 10:00–11:00.
- Зал «Большой» — 10:00–11:00 и зал «Переговорная 1» — 10:30–11:30.
- Любое количество онлайн-встреч в одно время.

Не разрешено только пересечение интервалов в одном и том же физическом зале. Отменённые и завершённые встречи не занимают зал.

## Обязательная настройка секретов на сервере

В `.env` укажите три разных случайных секрета длиной не менее 32 случайных байт:

```dotenv
DB_PASSWORD=<уникальный пароль пользователя MySQL>
DB_ROOT_PASSWORD=<другой уникальный пароль root MySQL>
REDIS_PASSWORD=<третий уникальный пароль Redis>
```

Генерация в PowerShell:

```powershell
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
[Convert]::ToHexString($bytes).ToLower()
```

Лучше генерировать секреты криптографически надёжным генератором, например `openssl rand -hex 32`, если OpenSSL установлен. Не отправляйте секреты в чат и не храните `.env` в Git.

Если база данных уже создана, изменение `DB_PASSWORD`/`DB_ROOT_PASSWORD` только в `.env` не меняет пароли внутри существующего MySQL автоматически. Сначала согласуйте смену пароля пользователя MySQL и обновите `.env`; не удаляйте том БД.

## Развёртывание

Из каталога проекта:

```powershell
docker compose config
docker compose --profile bot up -d --build backend queue scheduler vks-bot frontend nginx
docker compose exec backend php artisan migrate --force
docker compose exec backend php artisan optimize:clear
docker compose restart backend queue scheduler vks-bot nginx
```

Не выполняйте `docker compose down -v`: команда может удалить данные БД и файлы приложения в томах.

## Что ещё нужно для production

- Публиковать сайт только через HTTPS (TLS на reverse proxy/корпоративном шлюзе), особенно если пользователи входят с разных устройств.
- Ограничить доступ к порту 80/443 межсетевым экраном корпоративной сетью/VPN, если сайт внутренний.
- Настроить ежедневные резервные копии MySQL с проверкой восстановления и отдельным хранением вне сервера.
- Периодически менять токен бота SaluteJazz и токены MAX; не передавать их во фронтенд.
- Включить мониторинг свободного места, RAM, CPU, очереди и ошибок Laravel/Nginx.

## Границы проверки

Статические проверки не заменяют испытания на сервере. В текущей среде проверены PHP-синтаксис, Python-компиляция, shell-синтаксис, YAML Docker Compose и синтаксис Nginx. Docker daemon, MySQL, Node dependencies и реальный сайт SaluteJazz в этой среде недоступны, поэтому сборка контейнеров, `npm run build`, миграция на копии production-БД, нагрузочное тестирование и сквозные браузерные сценарии должны быть выполнены на тестовом сервере перед боевым запуском.

## Резервные копии: проверка целостности и контроль свежести

Команда `php artisan db:backup --keep=14` теперь использует временный MySQL option-файл с правами `0600` (пароль не передаётся аргументом процесса), потоково создаёт gzip-архив, проверяет его командой `gzip -t`, рассчитывает SHA-256 и сохраняет метаданные рядом с архивом. Неудача копирования отправляет предупреждение администратору. Вкладка «Администрирование → Статус системы» показывает свежесть последней проверенной копии и обновляется раз в минуту, пока открыта.

Для работы backup-команды в backend-образ добавлены `mariadb-client` и `gzip`. После изменения Dockerfile образ backend/queue/scheduler необходимо пересобрать. Резервные копии не следует публиковать через Nginx или отдавать обычным пользователям.
