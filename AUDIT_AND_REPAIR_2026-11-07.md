# BCS — техническое обновление и аудит (07.11.2026)

## Что изменено

### 1. Параллельное создание ВКС
- Laravel по умолчанию использует `database` queue вместо `sync`.
- Queue container запускает два независимых worker-процесса (`QUEUE_WORKERS=2`) и автоматически перезапускает worker, если тот завершился.
- `vks-bot` запускает два независимых worker-потока; каждый поток создаёт и использует собственный экземпляр Playwright/Chromium в том же потоке. Сессии и страницы не разделяются между задачами.
- До двух комнат создаются одновременно. Дополнительные задачи остаются в очереди; очередь ограничена 20 ожидающими запросами в сервисе бота и возвращает 503 при переполнении.
- Один и тот же meeting не может параллельно запустить несколько одинаковых задач (`ShouldBeUnique`).
- Разные залы могут иметь ВКС в одинаковое время. Для одного физического зала пересекающиеся интервалы блокируются атомарной MySQL advisory-lock проверкой. Повторяющиеся встречи также учитываются в проверке.

### 2. Безопасность бота
- `BOT_TOKENS` больше не передаётся через `VITE_*` и не встраивается в JavaScript frontend.
- Браузер больше не обращается к `vks-bot` напрямую: создание выполняется серверным Laravel Job.
- Вызовы бота разрешены только с серверным `X-Bot-Token`; пустой `BOT_TOKENS` закрывает доступ (503), неправильный токен — 401.
- Nginx закрывает публичные `/vks-bot/create`, `/create-link`, `/check-and-create`; backend вызывает бот по внутренней Docker-сети.
- Удалено отражение произвольного Origin в CORS-заголовках с credentials. Production frontend/API обслуживаются на одном origin; для dev используется Vite proxy.
- Старый токен, который ранее мог быть включён в клиентскую сборку, необходимо заменить новым.

### 3. Статус создания ссылки и повторная попытка
- Добавлена миграция `vks_link_status`: `not_required`, `pending`, `creating`, `created`, `failed`.
- Ссылка создаётся после сохранения встречи в фоне; форма не ждёт Playwright.
- Если SaluteJazz не создал комнату, фиктивный случайный URL не сохраняется. Статус становится `failed`.
- Организатор/администратор/модератор может повторить создание ссылки из карточки встречи.
- После готовности или ошибки ссылка/статус инвалидируют кэш расписания; главная временно опрашивает список чаще, пока есть `pending`/`creating`.
- Уведомление о готовой ссылке использует существующий допустимый тип `info`.
- Автопилот не ставит задачи в очередь, если реальный бот отключён.

### 4. Защита расписания
- При создании, редактировании и переносе проверяются пересечения в том же физическом зале.
- MySQL advisory lock удерживается до commit/rollback, поэтому два одновременных запроса не могут одновременно увидеть один и тот же слот свободным.
- Проверка учитывает повторяющиеся встречи в пределах горизонта `RecurrenceService`.
- Разные залы и онлайн-встречи не блокируют друг друга по времени.
- Закрытые дни не превращены в запрет бронирования: виджет свободных залов сохраняет отображение интервалов 08:00–20:00 и позволяет выбирать свободные слоты на выходных/следующих датах.

### 5. Docker и файловый кэш
- Добавлен `backend/docker-entrypoint.sh`: при каждом старте контейнера создаёт Laravel storage/cache/session/view/log directories и восстанавливает права на общих volumes. Это устраняет повторение `fopen(...storage/framework/cache/data...): No such file or directory` на старых Docker volumes.
- Queue и scheduler работают от `www-data`, чтобы общие cache/log-файлы оставались доступны PHP-FPM.
- `DB_QUEUE_RETRY_AFTER=300`, worker timeout 240 секунд.
- Для двух headless Chromium workers лимит `vks-bot` увеличен до 2 ГБ RAM и 2 CPU.

### 6. Frontend и ранее добавленные функции
- Сохранены: ближайшая/следующая ВКС, даты на ТВ-экранах, отдельная страница всех ВКС зала, выбор даты для свободных залов, двустороннее смещение времени на 30 минут.
- Статус «Бот создаёт ссылку…» показывается на главной; после ошибки доступна повторная попытка.
- Частое обновление данных главной включается только при создании ссылки; в обычном режиме остаётся редкое обновление.

## Настройки `.env`

Для реального автоматического создания комнат задайте значения в корневом `.env` (не отправляйте токен в чат):

```env
BOT_TOKENS=<новый длинный случайный секрет>
VKSBOT_EXPECTED=true
VKSBOT_AUTO=true
VKSBOT_CONCURRENCY=2
VKSBOT_QUEUE_LIMIT=20
QUEUE_CONNECTION=database
QUEUE_WORKERS=2
DB_QUEUE_RETRY_AFTER=300
```

Сгенерировать случайный секрет в PowerShell:

```powershell
$token = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
$token
```

Скопируйте значение только в `.env` на сервере в `BOT_TOKENS=`. Не используйте старый токен, если он когда-либо был включён в Vite frontend build.

## Развёртывание на Windows / Docker Compose

Из `D:\server\BCS` после обновления файлов и правки `.env`:

```powershell
docker compose --profile bot up -d --build backend queue scheduler vks-bot frontend nginx
docker compose exec backend php artisan migrate --force
docker compose exec backend php artisan optimize:clear
docker compose restart backend queue scheduler vks-bot nginx
```

Не выполняйте `docker compose down -v`: это может удалить постоянные volumes/данные.

Проверка:

```powershell
docker compose ps
docker compose logs --tail=100 queue
docker compose logs --tail=100 vks-bot
docker compose exec backend php artisan schedule:list
```

В `vks-bot` `/health` показывает `workers`, `active`, `queued`. При корректной конфигурации ожидается `workers: 2`.

## Что не удалось проверить в этой среде

- Полный `npm ci`/`npm run build` и `tsc --noEmit`: установка зависимостей не завершилась из-за сетевого таймаута обращения к npm registry.
- Реальный Docker build/compose up: Docker daemon/CLI в среде проверки отсутствует.
- Выполнение миграций и интеграционные тесты на MySQL: подключённой БД нет.
- Реальное создание комнаты на salutejazz.ru: внешняя форма/капча/доступность требуют проверки в вашем контейнере. Если SaluteJazz снова не покажет поле формы, бот сохранит `/tmp/vksbot_fail.png`; скопируйте его командой `docker compose cp vks-bot:/tmp/vksbot_fail.png .\vksbot_fail.png`.

Статические проверки не заменяют проверку в вашем рабочем Docker-окружении. После развёртывания нужно создать две тестовые ВКС в разных залах с одинаковыми датой/временем и убедиться, что обе получили реальные ссылки.
