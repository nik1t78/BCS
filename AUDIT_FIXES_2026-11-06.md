# Проверка и исправления BCS — 06.11.2026

## 1. Планировщик Laravel

**Найденная причина статуса «Планировщик молчит».** Проект использует Laravel 12 и регистрирует расписание через `bootstrap/app.php ->withSchedule(...)`. Метод `schedule()` из `App\\Console\\Kernel` при такой конфигурации не является активной точкой регистрации расписания. Heartbeat планировщика находился только в `Kernel.php`, поэтому `SystemStatusController` не получал свежий `cron_heartbeat.log` / `scheduler:heartbeat` и показывал простой, даже когда часть задач из `bootstrap/app.php` могла выполняться.

Исправлено:
- heartbeat добавлен в активный `bootstrap/app.php`: атомарная запись Unix timestamp в `storage/logs/cron_heartbeat.log` и дублирование в cache с TTL 3 минуты;
- `vks:autopilot` и `system:monitor`, ранее описанные только в неактивном Kernel-расписании, добавлены в активное расписание Laravel 12;
- добавлена ежедневная очистка старых `BotLog` и `TvViewLog`;
- удалён неподдерживаемый вызов `Schedule::registerCallback()` из legacy Kernel;
- статус системы больше не принимает аварийный маркер web-процесса за подтверждение работоспособности scheduler.

Активные задачи после исправления: напоминания ВКС (каждую минуту), автозавершение ВКС (каждую минуту), уведомления о конференциях (каждые 15 минут), очистка уведомлений (ежедневно), аналитика (ежедневно), очистка Sanctum-токенов (ежедневно), резервная копия БД (ежедневно в 02:30), монитор ВКС-бота (каждые 5 минут), автопилот ссылок ВКС (каждую минуту), системный монитор (каждые 5 минут), heartbeat (каждую минуту), ротация журналов (ежедневно).

## 2. Нагрузка главной страницы

- Главный Dashboard обновлял `currentTime` каждую секунду, что повторно рендерило всю страницу и тяжёлые дочерние компоненты.
- Обновление состояния главной страницы снижено до одного раза в минуту.
- Секундный обратный отсчёт вынесен в отдельный `React.memo` компонент `MeetingCountdown`; его секундные обновления не вызывают повторный рендер Dashboard, календаря и виджета залов.

## 3. Автоматическая длительность ВКС

- При изменении начала окончание автоматически становится на 30 минут позже.
- При изменении окончания начало автоматически становится на 30 минут раньше.
- Логика добавлена в обе формы (создание и редактирование).
- Предзаполнение с одним только временем начала рассчитывает окончание как `start + 30 минут`.
- Начальная длительность новой встречи по умолчанию — 30 минут.


## 4. Виджет «Свободные залы» — дополнительная проверка и исправления

Проверена цепочка `FreeRoomsWidget` → `GET /meetings/rooms-availability` → `RoomController::buildAllAvailability()` → расчёт свободных интервалов.

Найдены и исправлены дополнительные ошибки:
- Минутный кэш фронтенда не сохранял `hoursById`; после первого минутного обновления индивидуальный график зала мог заменяться графиком по умолчанию. Теперь кэширует и часы работы.
- При ошибке расчёта доступности backend мог вернуть `degraded: true` и пустые `busy`; фронтенд трактовал это как полностью свободные залы. Теперь degraded-ответ не считается достоверной доступностью.
- При ошибке fallback-запроса занятость больше не подменяется пустым массивом. Для такого зала не создаются кликабельные свободные слоты, выводится предупреждение «Не удалось проверить занятость».
- Закрытый день (`hours: null`) больше не приводит к созданию свободных слотов по резервному графику. Закрытые залы остаются в ответе API и показываются как закрытые, а не как «залы не настроены».
- Свободный интервал, пересекающий текущее время, теперь делится на прошедшую и будущую части. Например, при окне 08:00–12:00 и времени 10:15 часть 08:00–10:15 недоступна, а 10:15–12:00 остаётся доступной.
- При создании и удалении зала сбрасывается кэш доступности. При переименовании зала в транзакции обновляются ссылки на него в существующих встречах, иначе занятость по старому названию могла не учитываться.
- Блоки занятости, выходящие за границы отображаемой шкалы, обрезаются по видимой области.

Локальный тест расчёта свободных интервалов пройден: проверено разделение прошедшей/будущей части, полностью занятый день и будущая дата.

## 6. Что требуется проверить на сервере после обновления

Выполнить в каталоге проекта:

```bash
docker compose up -d --build backend queue scheduler
docker compose exec backend php artisan optimize:clear
docker compose restart scheduler

docker compose ps scheduler
docker compose exec scheduler php artisan schedule:list
docker compose exec scheduler php artisan schedule:run -v
docker compose logs --tail=100 scheduler
docker compose exec backend sh -lc 'cat storage/logs/cron_heartbeat.log'
```

Проверка «Свободных залов» на сервере:
1. Открыть один и тот же день под администратором и обычным пользователем — список и занятость должны совпадать.
2. Создать тестовую ВКС в зале, например 11:00–11:30. После сохранения этот интервал должен стать занятым; после переноса — освободиться в старом времени и заняться в новом.
3. Проверить повторяющуюся ВКС на дате одного из её повторов.
4. Проверить зал с индивидуальным графиком и закрытый день.
5. Проверить, что при недоступном API/ошибке сервера интерфейс не предлагает забронировать непроверенный слот.
6. Проверить клик по свободному 30-минутному сегменту: форма должна открыться с выбранными залом, датой и временем.

Через 1–2 минуты после обновления открыть админка → Статус системы: «Планировщик» должен показывать свежий цикл (не более 150 секунд). Для уведомлений проверить тестовую встречу с участниками и фактическое появление записей в `notifications`/интерфейсе.

## Ограничения проверки

В переданном архиве отсутствуют `node_modules` и `backend/vendor`; в окружении проверки нет Docker и подключённой MySQL. Поэтому полную Vite production-сборку, полноценный `tsc --noEmit`, `artisan schedule:list`, выполнение команд по реальной БД и браузерные сценарии здесь выполнить нельзя. Локальные проверки синтаксиса и алгоритма не заменяют runtime-тестирование на сервере. Поэтому нельзя честно утверждать, что реальные свободные залы и доставка уведомлений уже подтверждены на работающем сервере — исправлена логика кода, для фактического подтверждения нужен запуск проекта.
