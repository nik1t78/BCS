# Управление ошибками очереди

## Где находится

Войдите под учётной записью администратора и откройте:

**Админка → Статус системы → Ошибки очереди**.

Раздел показывает последние неудачные задания из таблицы Laravel `failed_jobs`. В интерфейс не передаются сериализованный payload задания и полный stack trace: показывается только первая строка исключения с базовой маскировкой значений Bearer/password/token/secret.

## Повтор задания

1. Убедитесь, что причина ошибки устранена (например, доступна БД или настроена интеграция).
2. Нажмите **Повторить** у конкретного задания.
3. Backend вызывает штатную команду Laravel `queue:retry` по UUID. Задание возвращается в исходную очередь; дальнейшее выполнение зависит от работающего queue worker.
4. Проверьте результат в статусе системы и журнале контейнера `queue`.

Кнопка не запускает все ошибки разом — задания повторяются по одному.

## Удаление записи об ошибке

Кнопка **Удалить** удаляет только запись из `failed_jobs`. Задание не будет повторно выполнено. Используйте действие только после проверки причины ошибки.

## Диагностика на сервере

Из каталога проекта:

```powershell
docker compose ps
docker compose logs --tail=100 queue
docker compose logs --tail=100 scheduler
docker compose logs --tail=100 backend
```

Список ошибок через Artisan:

```powershell
docker compose exec backend php artisan queue:failed
```

Повтор одной задачи вручную:

```powershell
docker compose exec backend php artisan queue:retry <UUID>
```

Не используйте `queue:retry all` без проверки причины массового отказа. Не очищайте таблицы `jobs` или `failed_jobs` вручную и не запускайте `migrate:fresh` на рабочей базе.

## Ограничения

- Раздел доступен только администратору.
- При недоступной или отсутствующей таблице `failed_jobs` API возвращает понятный статус 503; сначала проверьте состояние БД и миграций.
- Успешный ответ «возвращено в очередь» означает, что Laravel принял задачу обратно, а не что внешняя интеграция уже успешно выполнилась.
