# Phase 38 — точность мониторинга очереди и планировщика

## Найденная проблема

В `Kernel.php` существовала scheduled-задача `queue-heartbeat-fallback`: если heartbeat очереди устаревал, сам планировщик записывал свежее значение в тот же cache key, который использовался как сигнал жизни queue worker. При остановленном контейнере очереди это могло показывать воркер как работающий, хотя `queue:work` уже не выполнялся.

## Исправление

- Удалена задача, которая синтезировала heartbeat очереди со стороны scheduler.
- Единственный источник heartbeat — `queue:heartbeat`, который перед записью проверяет наличие реального процесса `php artisan queue:work`.
- Если процесс не обнаружен, sidecar очищает cache fallback; устаревший файловый timestamp больше не считается свежим после истечения порога.
- Удалена дублирующая задача очистки `tv_view_logs`: ранее две задачи с одинаковым именем запускались по разным срокам хранения (30 и 60 дней). Сохранена действующая политика очистки записей старше 30 дней.

## Регрессионные проверки

Расширен `queue-heartbeat-policy-smoke.php`:
- планировщик не содержит синтетический queue heartbeat;
- для TV view logs зарегистрирована только одна задача хранения;
- sidecar heartbeat проверяет реальный процесс queue worker.

Существующий шаг CI уже запускает этот smoke test; отдельная новая миграция или изменение схемы БД не нужны.

## Сохранность и границы

- Не меняются таблицы, данные, миграции, `.env`, Docker volumes и публичные API.
- В админке статус очереди теперь может показывать реальный отказ, если sidecar heartbeat не работает; это намеренно, вместо ложного «OK».
- GitHub CI не заменяет остановку/запуск контейнера queue в тестовом Docker окружении. Нужно отдельно проверить: живой worker = heartbeat обновляется; остановленный worker = heartbeat стареет и статус становится DOWN.
